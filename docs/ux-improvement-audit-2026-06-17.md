# UX改善調査レポート: ありものdeレシピ

作成日: 2026-06-17

調査対象:

- Vite + TypeScript + CSS のフロントエンド
- Cloudflare Pages Function `/api/recipe`
- prompt生成、候補値、フォーム、モバイル固定フッター、AI結果表示、テスト
- スマホ幅 390x844 でのローカル実画面確認

## 1. エグゼクティブサマリー

### 現状UXの総評

現状の「ありもの de レシピ」は、家庭料理向けのAIプロンプトメーカーとしてはかなり丁寧に作られている。特に、未指定項目を出力しないこと、家にない主材料を追加させないこと、コピー導線を残すこと、同一オリジン `/api/recipe` 以外へ送信しないことは明確に守られている。`src/prompt.ts` は条件付きセクションを丁寧に組み立てており、`src/combo-registry.ts` は候補入力、自由入力、IME、チップ編集をかなり細かく扱っている。

一方、North Star を「家にある食材だけで、今すぐ作れる納得感のある料理を、最短・最少入力・最少迷いで決められること」と置くなら、現状はまだ最短距離ではない。現行の中心体験は「料理を決める」ではなく「AIへ渡す依頼文を作る」であり、ユーザーは料理候補を比較して決める前に、入力フォーム、依頼文確認、コピー/AI生成というプロンプト中心の工程を通る。

### 最も深刻なUX課題

最も深刻な課題は、プロダクトの主目的がユーザーの期待する「今日作る料理の決定」ではなく、内部成果物である「レシピ依頼文」に寄っていること。`src/ui.ts` のメイン導線は、ヘッダーの使い方も `1. 条件を入力 -> 2. 依頼文ができる -> 3. AI生成またはコピー` になっており、`src/output-panel.ts` も prompt preview と copy flow が中心である。

### 最も大きな改善余地

最も大きな改善余地は、AIレスポンスをプレーンテキストの1件表示から、構造化された複数候補、比較、決定、調理モードへ変えること。`src/ai-recipe-panel.ts` は `recipe.textContent = aiRecipe.recipe` でAI結果をそのまま表示しているため、候補比較、材料不足、代替、信頼度、調理中ステップ、再生成チップをUIで扱えない。

### 抜本的に変えるべきかどうかの結論

UX最大化を目的にするなら、抜本的に変えるべき。現状の延長では「プロンプトをうまく作れるアプリ」にはなれるが、「忙しい家庭料理ユーザーが今日作るものを最短で決めるアプリ」には届きにくい。

ただし、これはADR 0011の承認済み範囲を超える提案を含む。現行ADRでは `レシピ依頼文` がコア成果物であり、コピー導線を第一級に保つ必要がある。したがって、実装に入る前に「プロンプトメーカーを主価値に残すのか、AIレシピ決定プロダクトへ主価値を移すのか」を人間が判断する必要がある。

### 優先すべき改善テーマ上位5つ

1. 「依頼文を作る」から「料理を決める」へ主導線を変更する。
2. AI出力を構造化JSONにして、複数候補、材料充足、不足、代替、理由、調理ステップをUIで扱う。
3. スマホ片手操作向けに、入力を「冷蔵庫確認モード」と「今日の制約だけ」へ圧縮する。
4. 調理中UXを追加し、1ステップ表示、タイマー、画面維持、音声/大ボタン操作を用意する。
5. 履歴、家族プロフィール、常備調味料、好み/アレルギーを保存し、毎日の再入力を減らす。

## 2. 現状のユーザーフロー

コードから読み取れる現在の流れは次の通り。

1. ユーザーがアプリを開く。
   - `src/main.ts` が `initializeApp(app)` を呼び、`src/ui.ts` が全画面を文字列HTMLで描画する。
2. ユーザーが `今回やりたいこと` を選ぶ。
   - 選択肢は `ありものでおまかせ`、`作りたい料理がある`、`一緒に出す料理に合わせたい`。
   - `syncIntentSections()` が `作りたい料理` や `一緒に出す料理`、`作りたい品数` の表示を切り替える。
3. ユーザーが `家にある食材・材料` を入力する。
   - `src/combo-registry.ts` が候補検索、自由入力、Enter確定、チップ化、削除、編集を扱う。
   - 候補値は `src/candidate-values/` にあり、食材は206候補、調理方法・調理器具は71候補、方向性は89候補、合わせる料理は167候補ある。
4. 必要なら `材料の使い方` で、材料ごとに `おまかせ`、`必ず使う`、`使い切る` を選ぶ。
   - `src/ui.ts` の `renderMaterialUsePanel()` が、入力済み材料に紐づいた行を描画する。
5. 人数、品数、調理器具、調理時間、方向性、使えない食材、その他要望を指定する。
   - 多くは折りたたみUIとして `renderCollapsibleField()` で描画される。
6. `src/conditions.ts` が現在の入力状態を `PromptData` に集約する。
7. `src/prompt.ts` の `buildPrompt(data)` がレシピ依頼文を生成する。
   - 未指定項目は出さない。
   - `買い足しを前提にせず、家にない主材料を追加しない` などのルールを含める。
   - `代用案`、`保存方法`、`栄養解説`、`献立全体の追加提案` は出力しないよう指示している。
8. ユーザーは出力された依頼文を確認する。
   - デスクトップでは右側の `prompt-section`、モバイルでは固定ボトムシートで確認する。
9. ユーザーはどちらかを選ぶ。
   - `AIでレシピを作成`: `src/ai-recipe-client.ts` が同一オリジン `/api/recipe` にpromptを送る。
   - `AI向けレシピ依頼文をコピー`: clipboardへコピーし、ChatGPT/Claude/Geminiなどへ貼る。
10. アプリ内AI生成の場合、`functions/api/recipe.ts` が Workers AI に送信し、文字列のレシピ案を返す。
11. `src/ai-recipe-panel.ts` が成功/失敗/ローディングを表示する。
   - 成功時はAIの返した文字列を `white-space: pre-wrap` のテキストとして表示する。

実画面確認では、390x844 viewportの初期ページ全体高さは3237pxで、約3.84画面分だった。材料3つ、2人分、20分以内、やさしい味を入れた場合の依頼文は2177文字だった。

## 3. 理想のユーザーフロー

スマホで「今すぐありもので作る」状況に最適化するなら、理想フローは次のようにする。

1. ユーザーがアプリを開く。
2. ファーストビューに `今日、家にあるもので何作る？` と、食材入力だけを大きく出す。
3. ユーザーは食材を1つずつ入れる。音声、チップ、よく使う食材、前回食材、期限近い食材をワンタップで追加できる。
4. 食材が1つでも入ったら、AI生成を待たずに簡易候補を即時表示する。
   - 例: `卵 + 豆腐 + もやしなら、炒め物/スープ/卵とじが合いそう`
5. `10分以内`、`子ども向け`、`洗い物少なめ`、`ボリューム重視` などの制約はチップで後から足す。
6. ユーザーが `この条件で候補を見る` を押す。
7. AIは構造化JSONで3候補を返す。
   - 各候補に、料理名、使う食材、買い足しゼロ/不足あり、調理時間、洗い物量、子ども適性、理由、信頼度を付ける。
8. ユーザーは候補カードを比較し、1つ選ぶ。
9. レシピ詳細では、材料、下ごしらえ、手順、注意、味調整だけを短く見る。
10. `作る` を押すと調理モードへ入る。
11. 調理モードは1ステップずつ大きく表示し、タイマー、次へ、戻る、材料を見るを大きな操作で出す。
12. 作り終わったら、履歴に保存し、家族の反応、使い切れた食材、次回避けたいものを軽く記録できる。

## 4. サブエージェント別レビュー

### 4.1 モバイルUXエージェント

#### 発見した問題

- 初期画面が約3.84画面分あり、最初の価値に到達するまで長い。
- モバイルでは `sticky-footer.ts` が幅1024px未満で常に固定フッターを表示するため、入力前から下部を大きく占有する。
- 固定フッターの主CTAが `AI向けレシピ依頼文をコピー` で、料理決定より依頼文作成が目立つ。
- `今回やりたいこと`、材料、材料の使い方、人数、折りたたみ項目が続き、疲れているユーザーには情報量が多い。
- ボトムシート内のコピー成功文言が長く、実画面では緑の大きな丸い塊のように表示され、視認性が悪い。
- キーボード表示時のフッター圧迫はコード上で明示的に扱っていない。
- 調理中に使う画面がなく、濡れた手で見る/操作する前提になっていない。

#### なぜ問題か

想定ユーザーは冷蔵庫を見ながら片手でスマホを操作している。初期状態で入力以外の説明や固定フッターが大きいと、冷蔵庫確認中の視線移動が増える。さらにCTAが「コピー」中心だと、ユーザーは「ここで料理が決まる」という感覚を持ちにくい。

#### 改善案

- 初期ファーストビューは食材入力と `候補を見る` のみに近づける。
- 固定フッターは入力後に出す。または初期は高さを小さくし、主CTAを `料理候補を見る` にする。
- ボトムシートは依頼文表示ではなく、候補比較と調理開始の場所に変える。
- キーボード表示時は入力欄直下に候補、画面下部に小さな確定CTAだけを出す。
- 調理モードでは大きい文字、1ステップ表示、左右スワイプ、大きな次ボタンを使う。

#### 抜本改善が必要か

必要。モバイルの第一体験を `依頼文確認` から `食材入力 -> 候補決定` へ変えるべき。

### 4.2 料理ユーザー理解エージェント

#### 発見した問題

- 食材入力は自由入力と候補チップが強いが、冷蔵庫を見ながら「少しだけ残っている」「期限が近い」「冷凍」「開封済み」を表現しにくい。
- 常備調味料が毎回暗黙扱いで、家庭差を反映しにくい。
- 家族人数はあるが、家族ごとの好み、アレルギー、子ども向け、大人向けの継続情報がない。
- `作り置き多め` はあるが、保存日数や弁当向け、翌日使い回しなどの現実的分岐が弱い。
- 洗い物量、火を使わない、包丁なし、疲れている、夜遅いなどの料理現実が前面に出ていない。

#### なぜ問題か

家庭料理の意思決定では、材料名だけでなく、量、鮮度、家族の反応、調理負荷、後片付けが大きい。現状はプロンプトにそれらを自由文で入れれば扱えるが、疲れているユーザーに自由文入力を求めるのは負荷が高い。

#### 改善案

- 食材チップに `少しだけ`、`使い切りたい`、`期限近い`、`冷凍`、`開封済み` を付けられるようにする。
- 初回設定で常備調味料を選ぶ。
- 家族プロフィールに年齢層、好き嫌い、アレルギー、辛さ耐性を持たせる。
- `洗い物少なめ`、`包丁少なめ`、`火を使わない`、`弁当向け`、`作り置き` を上位チップにする。
- 候補カードに `使い切れる食材` と `残る食材` を表示する。

#### 抜本改善が必要か

必要。食材は単なる文字列から、料理決定に必要な軽い構造を持つ入力へ変えるべき。

### 4.3 AIプロダクトUXエージェント

#### 発見した問題

- AIへの入力はprompt文字列中心で、アプリ内では構造化されたAI応答を扱っていない。
- 生成結果は1つの文字列で表示され、候補比較ができない。
- 不足食材ゼロか、どの材料を使ったか、なぜその提案かがUIとして保証されない。
- 失敗時はコピー導線に戻すだけで、再試行、条件を軽くする、別候補を見るなどがない。
- `もっと簡単に`、`10分以内に`、`子ども向けに` などの再生成導線がない。
- Workers AIのモデルは `@cf/meta/llama-3.2-3b-instruct` で、複雑な家庭料理制約と構造化品質を安定させるには評価が必要。

#### なぜ問題か

AIに慣れているユーザーほど、長いプロンプトや長い回答の読解を避けたい。欲しいのは「候補」「理由」「これで買い物なしでいけるか」の短い判断材料であり、AIの長文回答ではない。

#### 改善案

- `/api/recipe` のレスポンスをJSON化する。
- まず3候補を返し、候補一覧で比較する。
- 候補ごとに `不足食材ゼロ`、`使う食材`、`使わない食材`、`代替可`、`調理時間`、`洗い物量`、`信頼度` を出す。
- 再生成チップを候補カードや詳細画面に置く。
- ストリーミングまたは段階表示で、待ち時間中に `材料を確認中`、`買い足しなし候補を優先中` などを出す。

#### 抜本改善が必要か

必要。AIを「プロンプト送信先」ではなく「料理決定エンジン」として設計し直すべき。

### 4.4 情報設計・導線エージェント

#### 発見した問題

- 情報構造が `入力 -> 依頼文 -> 実行方法` で、料理候補や調理開始が後段にない。
- ファーストビューの使い方が「依頼文ができる」を強調し、ユーザーの本当のゴールである料理決定とズレる。
- 入力済み情報はチップで見えるが、候補決定後の保存、戻る、条件変更、比較がない。
- 依頼文textareaがユーザーの注意を取るが、一般ユーザーにとっては内部情報である。
- 履歴、お気に入り、最近作ったものを避ける機能がない。

#### なぜ問題か

料理中・家事中のユーザーにとって、内部promptは読まなくてよい情報である。確認すべきなのは「この食材で何が作れるか」「なぜそれでいいか」「今すぐ作れるか」。

#### 改善案

- 第一導線を `食材入力 -> 候補を見る -> 決める -> 作る` にする。
- 依頼文は詳細/開発者向け/コピー用の二次導線に下げる。
- 生成結果から条件変更へ戻れる再編集導線を入れる。
- 候補一覧、詳細、調理モード、履歴を画面概念として分ける。

#### 抜本改善が必要か

必要。画面構成を作り直すべき。

### 4.5 UIライティング・マイクロコピーエージェント

#### 発見した問題

- `AIへそのまま渡せるレシピ依頼文`、`AI向けレシピ依頼文をコピー` など、ユーザー価値より内部成果物名が目立つ。
- コピー成功文言 `コピーしました。普段使っているAIに貼り付けてください。` が長く、モバイルボタン内で破綻しやすい。
- `材料の使い方` の `必ず使う・使い切りたい食材・材料がある` は長く、疲れているユーザーには読みづらい。
- エラー時は `AI向けレシピ依頼文をコピーして...` に戻すため、ユーザーの「今決めたい」に寄り添いきれていない。
- ローディング文言が `AIにレシピ案を依頼しています。` だけで、何をしているかの安心感が弱い。

#### なぜ問題か

料理中のユーザーは説明を読みたいのではなく、判断したい。コピーや依頼文などのメタな言葉が前面に出ると、操作の意味を理解する負荷が増える。

#### 改善案

- H1/リードは `家にあるもので、今日作るものを決める` に寄せる。
- CTAは `料理候補を見る`、`これを作る`、`もっと簡単に` にする。
- コピー成功は短く `コピーしました` にし、詳細はトースト/補足に出す。
- 材料の使い方は `使い切りたい材料がある` に短縮する。
- ローディングは `買い足しなし候補を探しています` など状況を伝える。

#### 抜本改善が必要か

必要。文言体系を「prompt作成」から「料理決定」へ変えるべき。

### 4.6 アクセシビリティエージェント

#### 発見した問題

- ラベルやARIAは比較的丁寧だが、AI結果の中身はテキスト塊で、構造化された見出し/リストとしてスクリーンリーダーに渡りにくい。
- ラジオinput自体は16px程度で、ラベル全体は大きいが、視覚的には丸い小さな選択部品が目立つ。
- ボトムシートが常時出るため、画面拡大やキーボード表示時に主内容が圧迫される可能性がある。
- 調理中に離れて読むための大きな文字モードがない。
- motion配慮は `prefers-reduced-motion` があるが、調理中利用や高齢ユーザー向けの表示密度調整はない。

#### なぜ問題か

料理中は視線距離が伸び、手が濡れ、短時間で見返すことが多い。通常のフォームアクセシビリティだけでなく、調理中の可読性が必要になる。

#### 改善案

- AI結果をセマンティックなカード、見出し、リスト、手順に分解する。
- 調理モードでは大きい文字、強いコントラスト、1ステップ表示にする。
- ボトム固定UIは入力・読書・調理それぞれで高さを変える。
- 重要な状態変化は短い `aria-live` と視覚トーストを分ける。
- コントラストは暖色系の薄い背景で不足しやすい箇所を実測する。

#### 抜本改善が必要か

必要。レシピ閲覧と調理モードのアクセシビリティを別設計にするべき。

### 4.7 パフォーマンス・体感速度エージェント

#### 発見した問題

- 初期JSは軽い構成だが、初期画面にフォーム全体とprompt生成機構が載るため認知的な初期表示は重い。
- AI生成は非ストリーミングで、待機中表示は短い文だけ。
- スケルトン、段階的進捗、キャンセル、再試行がない。
- ネットワークエラー時はコピーへ逃がすだけで、アプリ内での回復導線が弱い。
- オフライン/不安定回線時の状態がない。

#### なぜ問題か

AI待ち時間は、実時間より「何が起きているかわからない」ことが不安を増やす。料理決定の場面では、待っている間にも材料を見続けているため、進捗や代替行動が必要。

#### 改善案

- AI待機中に段階表示を出す。
- 最初に軽量なローカル候補/過去候補を即表示する。
- ストリーミングで候補カードから順に出す。
- 失敗時は `再試行`、`条件を減らす`、`依頼文コピー` の3択にする。
- オフライン時は保存済み履歴やコピー導線を出す。

#### 抜本改善が必要か

必要。AI待ちを単なるローディングから、意思決定を進める状態へ変えるべき。

### 4.8 レシピ品質・信頼性エージェント

#### 発見した問題

- prompt内には安全性、火通り、家庭料理品質、買い足し禁止が含まれており、依頼文品質は高い。
- しかし結果は自由テキストなので、アプリ側で買い足し違反、不足食材、危険手順、アレルギー配慮を検証できない。
- `代用案`、`保存方法`、`栄養解説` を出力しない設計は、promptメーカーとしては短く安全だが、UX最大化の観点では重要情報を欠くことがある。
- レシピ信頼度や「なぜこの候補か」がUIにない。

#### なぜ問題か

ユーザーはAI回答を完全には信用していない。特に「買い物なしでいけるか」「子どもに出せるか」「生肉や卵の火通りは安全か」は、明示されないと不安が残る。

#### 改善案

- AIレスポンスに `usesOnlyAvailableMainIngredients`、`missingIngredients`、`safetyNotes`、`whyThisWorks` を必須化する。
- 危険食材、アレルギー、妊娠中、幼児向けは安全メモを出す。
- 不足食材がある候補は明確に下げるか、別タブに分ける。
- 保存/作り置きはユーザーが指定した場合だけ出す。

#### 抜本改善が必要か

必要。レシピ品質をUIで検証・比較できる構造へ変えるべき。

### 4.9 継続利用・パーソナライズエージェント

#### 発見した問題

- ログイン、保存、履歴、常備調味料、家族プロフィール、お気に入りがない。
- 毎回、食材、人数、好み、避けたいものを入力する必要がある。
- 最近作ったものを避ける機能がない。
- 使い切れた食材や買わずに済んだ価値が可視化されない。

#### なぜ問題か

毎日の料理では、家庭ごとの制約がほぼ固定される。毎回入力させると、2回目以降の価値が伸びにくい。特にアレルギーや子どもの好みは忘れると危険/不満につながる。

#### 改善案

- ローカル保存から始める。ログインなしでも `家族設定`、`常備調味料`、`苦手/アレルギー`、`最近作った料理` を保存する。
- 候補生成時に最近作ったものを避ける。
- `また作る`、`家族に好評`、`次は避ける` の軽いフィードバックを追加する。
- 消費できた食材を履歴に残す。

#### 抜本改善が必要か

必要。ただし現行ADRでは persistence/storage は人間判断が必要。UX最大化なら追加すべき。

### 4.10 グロース・差別化エージェント

#### 発見した問題

- ChatGPTに直接聞くより便利な点は、候補入力とprompt生成のガードレール。
- しかし、AIに慣れたユーザーにとっては、最終的に長い依頼文をコピーするならChatGPT直入力との差別化が弱い。
- レシピサイトとの差別化である「広告なし・即決」はまだ結果UIに出ていない。
- 共有したくなる成果物や家族内共有がない。

#### なぜ問題か

選ばれる理由は「promptがきれい」ではなく、「買い物に行かなくて済んだ」「今日の献立がすぐ決まった」「調理中も見やすかった」になるべき。

#### 改善案

- ブランド価値を `買い物なしで決める` に寄せる。
- 候補カードで `買い足しゼロ` を強く表示する。
- 家族にLINEで共有できる短い献立カードを生成する。
- `冷蔵庫にあるもので3候補` という初回30秒の価値を作る。

#### 抜本改善が必要か

必要。差別化軸を「AI prompt補助」から「ありもの献立決定」へ変えるべき。

### 4.11 技術アーキテクチャ・実現方式エージェント

#### 発見した問題

- UIの描画責務が `src/ui.ts` に集中しており、画面追加が増えると見通しが悪くなる。
- `src/types.ts` の `PromptData` はprompt入力向けで、レシピ候補/調理手順/保存履歴の型がない。
- `src/ai-recipe-client.ts` と `functions/api/recipe.ts` は文字列recipeを返す前提。
- ストリーミング、構造化レスポンス、複数候補、再生成、履歴保存には新しい境界が必要。
- 現状のテストはpromptとフォーム挙動には強いが、AI品質評価、候補比較、調理モードには未対応。

#### なぜ問題か

今の構成は「フォームからpromptを作る」には適しているが、「AI料理体験の状態遷移」を増やすと、prompt文字列とUI状態が密結合になりやすい。

#### 改善案

- `RecipeCandidate`、`RecipeDetail`、`CookingStep`、`HouseholdProfile` の型を追加する。
- AI APIは `prompt` ではなく構造化 `RecipeRequest` を受ける。
- prompt textはコピー用の派生成果物にする。
- UIを `input`, `candidate-list`, `recipe-detail`, `cook-mode`, `settings/history` に分ける。
- AI品質評価用のfixtureとスナップショットテストを追加する。

#### 抜本改善が必要か

必要。AIレシピ決定プロダクトにするなら、アーキテクチャも変えるべき。

### 4.12 QA・失敗体験エージェント

#### 発見した問題

- 食材が少なすぎる場合、入力途中でもpromptはできるが、候補の不確実性はUIに出ない。
- 食材が多すぎる場合、候補比較や優先消費がない。
- 変な組み合わせ時はAI任せで、アプリ側の回復導線がない。
- API失敗時はコピー導線を出すが、再試行や条件修正が弱い。
- 入力途中リロード、保存、履歴復元がない。
- アレルギー、宗教、妊娠中など高リスク制約を専用入力として扱っていない。
- 調理器具がない、時間がない、家族に不評だった時の再生成導線がない。

#### なぜ問題か

料理決定では失敗時のリカバリーが重要。AIが期待外れでも、次にどう修正すればよいかが見えれば継続利用につながる。

#### 改善案

- 入力不足時は `まず2品だけでもOK` など軽い空状態を出す。
- 食材が多い時は `優先して使う` を3つまで選ばせる。
- AI失敗時は `もう一度`、`条件を減らす`、`依頼文コピー` を並べる。
- レシピ詳細に `合わない` ボタンを置き、理由チップから再生成する。
- 高リスク制約は設定/入力で明示的に扱う。

#### 抜本改善が必要か

必要。失敗体験をpromptコピーへの退避だけにしない設計が必要。

## 7. 抜本的に変えるべき点

- 現在の体験は、想定ユーザーの課題に対して最短距離になっているか:
  - なっていない。プロンプト作成としては筋が良いが、料理決定としては遠回り。
- 画面構成を作り直すべきか:
  - 作り直すべき。`入力フォーム + prompt preview` から `食材入力 + 候補一覧 + 詳細 + 調理モード` に変える。
- 食材入力体験を作り直すべきか:
  - 作り直すべき。ただし現行のチップ/候補/自由入力は活かす。足すべきは少量、期限、冷凍、使い切り、よく使う食材、音声。
- AI出力形式を作り直すべきか:
  - 作り直すべき。プレーンテキストではなくJSON schemaにする。
- レシピ表示体験を作り直すべきか:
  - 作り直すべき。候補比較、詳細、調理モードに分ける。
- 保存・履歴・パーソナライズを追加すべきか:
  - UX最大化なら追加すべき。ログインなしのローカル保存から始めるのが現実的。ただし現行ADRでは人間判断が必要。
- 技術アーキテクチャを変えるべきか:
  - AIレシピ決定プロダクトにするなら変えるべき。prompt文字列中心から、構造化request/response中心へ移行する。

結論として、現状の延長ではUX最大化は難しい。`レシピ依頼文` を第一級成果物として残すことはできるが、主価値は `今日作る料理を決める` に移すべき。

## 8. 推奨する新UXコンセプト

### コンセプト名

「冷蔵庫から30秒献立」

### 一言説明

家にある食材を入れるだけで、買い足しなしで作れる候補を比較し、そのまま調理モードへ進める。

### 主要画面

- ホーム/食材入力
- 料理候補一覧
- レシピ詳細
- 調理モード
- 履歴/お気に入り
- 家族・常備品設定

### 主要導線

1. 食材を入れる。
2. 候補を見る。
3. 候補を選ぶ。
4. 作る。
5. 履歴に残る。

### ユーザーが最初の30秒で体験する価値

- 食材を2〜3個入れるだけで、買い足しなし候補が出る。
- 各候補に `なぜこれが合うか` と `足りないものがあるか` が出る。
- 長文を読まずに1つ選べる。

### 既存のChatGPT利用との差別化

- promptを書かなくてよい。
- ありもの、買い足しなし、家族条件、調理負荷がUIで比較できる。

## 10. AI prompt / レスポンス設計の改善案

### 現状promptの問題

- prompt品質は高いが、UIで扱うには長い。
- 出力形式がMarkdown文字列で、アプリ側が候補単位で検証できない。
- `代用案`、`保存方法`、`栄養解説` を禁止しており、必要時のUX価値を捨てている。
- 不足食材や信頼度が構造化されていない。

### あるべき入力データ構造

```ts
type RecipeRequest = {
  intent: "decide-from-available" | "target-dish" | "pairing";
  availableItems: {
    name: string;
    amountText?: string;
    priority?: "normal" | "must-use" | "use-up";
    condition?: "fresh" | "near-expiry" | "leftover" | "frozen" | "opened";
  }[];
  household?: {
    servings?: string;
    members?: { type: "adult" | "senior" | "child" | "toddler"; count: number }[];
    allergies?: string[];
    dislikes?: string[];
    preferences?: string[];
  };
  constraints?: {
    maxCookTimeMinutes?: number;
    tools?: string[];
    avoidItems?: string[];
    workload?: "low" | "normal";
    dishCount?: number;
    mealContext?: string;
  };
  responseMode: "candidate-list" | "detail" | "regenerate";
};
```

### あるべきレスポンスJSON構造

```ts
type RecipeResponse = {
  candidates: {
    id: string;
    title: string;
    summary: string;
    fitScore: number;
    confidence: "high" | "medium" | "low";
    badges: string[];
    usesOnlyAvailableMainIngredients: boolean;
    usedAvailableItems: string[];
    unusedAvailableItems: string[];
    missingIngredients: {
      name: string;
      importance: "required" | "optional";
      substituteFromAvailable?: string;
    }[];
    cookTimeMinutes: number;
    workload: "low" | "medium" | "high";
    dishesToWash: "few" | "normal" | "many";
    childFriendly: "yes" | "adjust" | "no";
    whyThisWorks: string;
    ingredients: {
      name: string;
      amount: string;
      source: "available" | "seasoning" | "optional";
    }[];
    prepSteps: string[];
    cookingSteps: {
      text: string;
      timerSeconds?: number;
      safetyNote?: string;
    }[];
    tasteAdjustments: {
      ifTooStrong: string;
      ifTooWeak: string;
    };
    safetyNotes: string[];
  }[];
  cannotSatisfy?: {
    reason: string;
    conflictingConditions: string[];
    suggestedRelaxations: string[];
  };
};
```

### レシピ候補の出し分け

- まず不足食材ゼロ候補を優先。
- その中で `最短`、`子ども向け`、`ボリューム` など軸を分ける。
- 不足あり候補は別枠で表示し、主候補に混ぜない。

### 不足食材の扱い

- `required` 不足がある候補は原則出さない。
- `optional` 不足は候補カードに明示する。
- 代替できる場合は `家にあるXで代用` と表示する。

### 代替食材の扱い

- 現行promptでは代用案を禁止しているが、UX最大化では必要。
- ただし買い足し提案ではなく、家にある材料内の代替に限定する。

### 安全性・アレルギー配慮

- アレルギーは自由文ではなく専用配列で送る。
- 生肉、卵、魚は `safetyNotes` を必須にする。
- 幼児/妊娠中/高齢者が含まれる場合は警告を強化する。

### 再生成・条件変更の設計

- 前回requestと選択候補idを持つ。
- 修正チップを `regenerateInstruction` として送る。
- 例: `makeSimpler`, `under10Minutes`, `noSpicy`, `mustUse:itemId`, `avoid:itemId`。

### ストリーミング表示の設計

- まず候補タイトルだけ表示。
- 次に材料充足と時間を表示。
- 最後に詳細手順を埋める。
- UIは候補カード単位で更新できるようにする。

### hallucinationを減らす工夫

- 入力材料を `availableItems` として明示。
- `main ingredients must be subset of availableItems` をsystem/request両方に入れる。
- レスポンスに `usedAvailableItems` と `missingIngredients` を必須化し、UI側で検査する。
- JSON parse失敗時は候補表示せず、再試行/コピーへ誘導する。

## 14. 最終結論

### このアプリが現状のままで勝てるか

プロンプトメーカーとしては一定の価値があるが、毎日の料理決定プロダクトとしては現状のままでは勝ちにくい。AIに慣れたユーザーならChatGPTへ直接聞く選択肢があり、レシピサイトより速い価値もまだ「候補決定」や「調理中UX」として出し切れていない。

### 最も重要なUXの欠陥は何か

最も重要な欠陥は、ユーザーのゴールである `今日作る料理を決める` ではなく、内部成果物である `AIに渡す依頼文` が主役になっていること。

### 最も優先すべき改善は何か

最優先は、AI出力を構造化し、買い足しなしの複数候補を比較できる候補一覧を作ること。これがないと、材料入力を改善しても最後は長文AI回答の読解に戻ってしまう。

### 抜本的な再設計が必要か

必要。現状の延長ではUX最大化は難しい。コピー可能な依頼文を残しつつ、主導線を `食材入力 -> 候補比較 -> 作る` へ再設計すべき。

### どのような体験になれば、想定ユーザーに強く刺さるか

冷蔵庫を見ながら食材を2〜3個入れるだけで、30秒以内に `買い足しゼロで作れる候補` が3つ出る。ユーザーは `最短`、`子ども向け`、`洗い物少なめ` などの観点で一つ選び、そのまま大きな文字の調理モードで作れる。これなら、ChatGPT直接利用より速く、レシピサイトより迷わず、毎日の食事作りに実用として刺さる。
